# E2E ゲートプラグイン設計 — winuse で実機確認するまで AI に「完了」と言わせない

日付: 2026-10-26
状態: 設計（ブランチ `feature/e2e-gate-plugin`）。本文中の「私の判断」はブレインストーミングで設計者（Claude）が決めた点で、利用者が明示的に決めた点とは区別している。

## 1. 目的と背景

バイブコーディングでデスクトップアプリを作成・修正すると、単体テストや型チェックが緑でも実機では壊れていることがある。これまで利用者は「winuse で実機スモークして」と毎回指示してきた。この指示をしなくても、**UI に関わる変更をしたら AI が winuse で自分で実機確認するまで「完了」と言えない**状態を、Claude Code の Hooks で強制する。

これを winuse のリポジトリから **Claude Code プラグイン** として配布し、MDium に限らず一般のデスクトップアプリ開発で使えるようにする（利用者の決定）。最初の導入先は MDium（Tauri）で、試運転の結果は後日記事にする予定（記事は本件の範囲外）。

## 2. ゴール / 非ゴール / アンチゴール

**ゴール**
- UI 関連の差分が未検証のまま、AI がターンを「完了報告」で終えられない。
- UI 関連の差分が未検証のまま、`git commit` できない。
- 何をどこまで確認するかは AI が変更内容から毎回決める。ゲートが求めるのは「最後の UI 変更より後に winuse のアサーションが 1 件以上成功している」という証拠だけ。
- アプリの技術（Tauri / WPF / Electron など）や言語に依存しない。プロジェクトごとの違いは設定ファイルで吸収する。

**非ゴール**
- 保存済みシナリオの全件回帰をゲートで強制すること（将来の拡張。§9）。
- テストの観点が十分かどうかの保証。ゲートは「確認したか」を見るだけで、「十分に確認したか」は見ない。
- winuse MCP サーバー自体のプラグイン同梱（§4.1）。
- macOS / Linux 対応（winuse が Windows 専用のため）。

**アンチゴール**（技術的に動いても失敗とみなすもの）
- 小さな修正に対して重いテストを毎回強いられ、うっとうしくて外したくなる（利用者が挙げた懸念）。
- AI が利用者に判断を仰ぐ本当の質問をしたときにまでブロックされ続ける。
- AI が「実機スモークをお願いします」と機能確認を利用者に押し付けて終われる（利用者:「やってくれよ」と思う）。
- ゲートが黙って無効になっている（設定が無い・壊れている）のに、利用者が有効だと思い込む。
- 毎ターンの終わりが目に見えて遅くなる。

## 3. 利用者が決めたこと

- 配布形態: winuse リポジトリからの Claude Code プラグイン。
- ゲートは 2 か所の併用: コミット直前（PreToolUse）とターン終了（Stop）。
- Stop での発言の分類は **案 A（本体の Claude に自己分類させる）**。未検証なら 1 回だけブロックして分類と対応を指示し、2 回目の終了は通す。甘さが目立てば将来、別の Claude を呼ぶ案 B に切り替える。
- 実機確認の依頼（「スモークをお願いします」「動作確認してください」）は完了報告と同じ扱いでブロック対象。
- 利用者に渡してよいのは、デザインや使い勝手など**好みが入る主観的な評価だけ**。それも機能確認（アサーション成功）を済ませた後に限る。
- フック処理は PowerShell スクリプトで書く（winuse.exe のサブコマンドにはしない）。
- 対象にするのは **このセッションで内容が変わった UI ファイルだけ**。セッション開始時点で既に未コミットだった変更（利用者の手作業や別セッションの残り）は、Claude がさらに手を加えない限り対象外（§4.3）。
- Stop のブロックは **同じ変更内容に対して 1 回だけ**。一度ブロックした後、同じ内容のまま完了報告されても Stop は通り、その抜け道はコミット前のゲートが受け止める（§4.5）。

## 4. 構成

### 4.1 プラグインの置き場所と中身（私の判断）

```
.claude-plugin/marketplace.json          # リポジトリをマーケットプレイスとして追加できるようにする
plugins/winuse-gate/
  .claude-plugin/plugin.json
  hooks/hooks.json
  scripts/*.ps1                          # フック本体
  skills/winuse-e2e/SKILL.md             # AI 向けの確認手順
  README.md
```

- プラグイン名は `winuse-gate`。
- **winuse MCP サーバーは同梱しない。** 既存の利用者は README の手順（`claude mcp add winuse -- <path>\winuse.exe --mcp`）で登録済みで、同梱すると二重登録になり、ツール名も `mcp__plugin_winuse-gate_winuse__*` に変わる。プラグインの README で「winuse を MCP として登録しておくこと」を前提条件として示す。フックのマッチャーは、利用者が付けたサーバー名が `winuse` 以外でも拾えるよう、ツール名の末尾（`__assert_text` など）で判定する。
- 導入手順は `/plugin marketplace add straygizmo/winuse` → `/plugin install winuse-gate`。

### 4.2 プロジェクト設定 `.claude/winuse-gate.json`

導入先のリポジトリにコミットする。git のトップレベル直下の `.claude/winuse-gate.json` を読む（worktree でもそのチェックアウトのファイルを読む）。

```json
{
  "ui": ["src/**/*.tsx", "src/**/*.ts", "src/**/*.css", "src-tauri/src/**/*.rs"],
  "exclude": ["**/*.test.ts", "**/*.test.tsx"],
  "launch": "pnpm tauri dev で起動。ウィンドウタイトルは ^MDium。WebView2 のデバッグを有効にするには process_run の webview_debug=true。"
}
```

- `ui`: UI 関連とみなすファイルの glob（必須）。
- `exclude`: そこから除外する glob（任意）。
- `launch`: アプリの起動方法やウィンドウの見つけ方を AI 向けに書く自由記述（任意）。ゲートは読まず、スキルが AI に読ませる。
- SessionStart フックは、設定があれば §4.3 の基準を記録する。
- **設定が無いリポジトリではゲートは何もしない。** ただし沈黙はしない: winuse-gate が有効なのに設定が無いことを、セッション開始時（SessionStart フック）に 1 行だけ AI のコンテキストへ伝える（私の判断。アンチゴール「黙って無効」への対策）。設定が壊れている（JSON 不正、`ui` 欠落）場合はフックが stderr にエラーを出し、ゲートは通す（壊れた設定で作業が止まらないように）が、その旨をブロック理由と同じ経路で AI に伝えて利用者へ報告させる。

### 4.3 「未検証」の判定

時刻ではなく **ファイルごとの内容のハッシュ** で判定する（方式は私の判断、セッション単位にすることは利用者の決定）。内容のハッシュには git の blob id（作業ツリーは `git hash-object`、ステージは `git ls-files -s`）を使い、作業ツリーとステージを同じ物差しで比べる。削除は「削除」という特別な値として扱う。

- **UI ファイル**: `ui` に一致し `exclude` に一致するもの以外。追跡ファイルと未追跡ファイル（`.gitignore` 対象は除く）の両方。
- **dirty**: HEAD と内容が違う UI ファイル（変更・追加・削除）。
- **基準（baseline）**: SessionStart で、その時点の dirty な UI ファイルとそのハッシュを記録する。基準が無いリポジトリ（セッション中に作った worktree など）は「基準 = HEAD」とみなす。作りたての worktree は clean なので、これで正しく扱える。
- **対象ファイル**: dirty で、かつ現在のハッシュが基準のハッシュと違うもの（＝このセッションで内容が変わったもの）。基準時点から手を付けていない利用者の変更は対象外。
- **検証済みハッシュ**: winuse のアサーションが成功した時点の、全対象ファイルの（パス, ハッシュ）を記録する。
- **未検証ファイル** = 対象ファイルのうち、現在の（パス, ハッシュ）が検証済みハッシュに無いもの。
- **未検証の指紋**: 未検証ファイルの（パス, ハッシュ）を並べたもののハッシュ。§4.5 の「1 回だけ」に使う。

こうすると、確認後にさらに編集したファイルだけが自動的に未検証に戻り、`git add` やコミットだけでは状態が変わらない。コミットで HEAD と同じになったファイルは dirty でなくなるので対象から外れる。

### 4.4 証拠の記録（PostToolUse）

- 対象: winuse の `assert_text` / `assert_exists` / `assert_window` / `assert_file`（ツール名の末尾で判定）、および `scenario_run`。
- `tool_response` のテキスト JSON を読み、アサーションは `passed: true`、`scenario_run` はシナリオ全体が PASS のときだけ証拠とする。`check`（確率で答える）や `act` は証拠にしない（私の判断。決定的な確認だけを数える）。
- 成功時、その時点の全対象ファイルの（パス, ハッシュ）を検証済みハッシュに追記する。
- 状態は `${CLAUDE_PLUGIN_DATA}/state/<git トップレベルの絶対パスのハッシュ>/` の下に置き、リポジトリ内には書かない。検証済みハッシュはリポジトリ単位（セッションをまたいで有効）、基準と「ブロック済みの指紋」はセッション単位（`<session_id>.json`）。古いセッションのファイルや古い検証済みハッシュは適当に間引く（私の判断）。
- サブエージェント内で通ったアサーションも同じく証拠として数える。サブエージェントの終了（SubagentStop）にはゲートを置かない。最終的には親の Stop とコミット前のゲートが受け止める（私の判断）。
- このフックは決してブロックしない（記録だけ）。
- AI 自身は状態ファイルを書かない。記録はハーネスが実行するフックが行うので、AI が証拠を捏造できない。

### 4.5 ターン終了のゲート（Stop）

1. `stop_hook_active` が true なら通す（案 A の「2 回目は通す」。無限ループ防止も兼ねる）。
2. 設定が無ければ通す。
3. 未検証ファイルが無ければ通す。
4. 現在の未検証の指紋で、このセッションですでに 1 回ブロックしていれば通す（利用者の決定。同じ内容で何ターン会話が続いても、ブロックは 1 回だけ）。
5. それ以外は、指紋を「ブロック済み」に記録してから `{"decision":"block","reason": ...}` でブロックする。`reason` は AI への指示で、要旨は次のとおり。
   - UI 関連ファイル（件数と代表的なパス）が winuse で未検証であること。
   - 直前の発言が **完了報告**、または **機能面の確認を利用者に依頼するもの** なら、利用者に頼まず winuse で自分で確認し、アサーションを通してから報告し直すこと。確認の範囲は変更に見合った最小限でよい（スキル `winuse-e2e` を参照）。
   - 直前の発言が **利用者に判断を仰ぐ本当の質問**、または **途中経過や行き詰まりの報告** なら、そのまま終えてよい。
   - デザインや使い勝手の評価を利用者に頼むのは、機能確認を済ませた後に限る。その際は winuse の `screenshot` を添える。
   - 本当に自動で確認できない場合は、その理由を利用者にはっきり伝えて終えること。

reason の文面は英語（AI 向けで、言語を問わず通じるため。私の判断）。

### 4.6 コミット前のゲート（PreToolUse）

- 対象: Bash ツールと PowerShell ツールで実行される `git commit`（`if` フィールドの権限ルール構文で絞る）。Claude が普段使う書き方（`git commit ...`、`git -C <path> commit ...`、`cd <dir> && git commit ...` 程度）を拾えればよく、意図的なすり抜け（エイリアス、スクリプト経由など）まで防ぐことは狙わない（私の判断。ゲートは AI のうっかりを防ぐもので、攻撃者を想定しない）。
- **コミットされる UI ファイルだけを見る**（私の判断）: ステージされた UI ファイル（`-a` / `--all` やパス指定のときはそれで入る作業ツリーのファイル）のうち、§4.3 の未検証ファイルに当たり、コミットされる内容のハッシュが検証済みハッシュに無いものがあれば `permissionDecision: "deny"` と理由を返す。理由は「winuse で確認してからコミットすること」。UI ファイルを含まないコミット（バックエンドやドキュメントだけ）は、他に未検証の UI ファイルがあっても止めない。
- **逃げ道**: コミットメッセージに `winuse-gate: skip <理由>` を含めれば通す。理由が git 履歴に残るので、後から利用者が確認できる（私の判断）。スキルで「自動確認が本当に不可能な場合に限り、利用者に伝えた上で使う」と指示する。
- `git commit --amend` なども同じ扱い。

### 4.7 スキル `winuse-e2e`

AI に「何をどう確認するか」を教える。ゲートのブロック理由からもこのスキルを参照させる。

- `.claude/winuse-gate.json` の `launch` を読んでアプリを起動・接続する。
- 変更に見合った最小限の確認をする。文言の修正なら `assert_text` 1 回で足りる。新しい画面や操作の流れなら、その流れを実際に操作してから要所をアサートする。
- クリックや入力だけでは証拠にならない。必ず `assert_*` で結果を確かめる。
- 機能確認を利用者に頼まない。主観的な評価だけを、`screenshot` を添えて頼む。
- 繰り返し使えそうな確認は `scenario_save` でリポジトリに保存してよい（保存先は導入先の慣習に従う）。
- 自動で確認できない場合の扱い（利用者への説明、`winuse-gate: skip` の使い方）。

### 4.8 実装上の制約

- PowerShell スクリプトは Windows PowerShell 5.1 で動くこと（pwsh 7 必須にしない）。ファイルは ASCII のみで書く（BOM や文字化けを避ける）。
- フックは exec 形式で `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "${CLAUDE_PLUGIN_ROOT}/scripts/<name>.ps1"` として呼ぶ。
- git の作業ディレクトリはフック入力の `cwd` から決める（worktree 対応）。
- Stop と PreToolUse のフックは速く終わること（目安: UI 差分の計算込みで 1 秒前後）。毎ターン走るため。

## 5. 確認済みの Claude Code の仕様（2026-10-26、公式ドキュメント）

- プラグインは `hooks/hooks.json`（トップレベルに `"hooks"` キー）とスキルを同梱できる。`${CLAUDE_PLUGIN_ROOT}` はインストール先（更新で変わるので状態を書かない）、`${CLAUDE_PLUGIN_DATA}` はプラグインごとの永続ディレクトリ。
- PostToolUse の入力には `tool_name`、`tool_input`、`tool_response`、`cwd`、`session_id` がある。MCP ツールのマッチャーは正規表現が使える。
- Stop の入力には `stop_hook_active` と `last_assistant_message` がある。`{"decision":"block","reason":...}` で止めると `reason` が Claude への次の指示になる。連続 8 回のブロックで強制終了する上限がある。
- 同じイベントのフックは並列に実行される。`type: "prompt"` のフックはフック入力しか見えず、条件付きで呼べない（案 B を採らなかった理由）。
- PreToolUse は `if` フィールドで権限ルール構文による絞り込みができ、`permissionDecision: "deny"` で拒否できる。
- Windows では exec 形式で実在の exe（`powershell.exe` など）を呼ぶのが確実。

## 6. ビルダーに任せること

- スクリプトの分割と命名、状態ファイルの JSON 形式、指紋のハッシュ方式。
- glob の照合の実装（`git ls-files` の pathspec を使うか、自前で照合するか）。
- `tool_response` の形の違い（MCP の content 配列の中の text など）への対応。
- ブロック理由とスキルの細かい文面。
- テストの方法（Pester、使い捨ての git リポジトリを使った結合テストなど）。

## 7. 導入と試運転（MDium）

- MDium に `.claude/winuse-gate.json` を追加する（`launch` には `pnpm tauri dev` と `webview_debug` の注意を書く）。
- プラグインをローカルのマーケットプレイスとして入れ、MDium で小さな UI 修正を数回行い、次を観察する。
  - 文言の修正 1 件で、最小限の確認で通過できるか。
  - 判断を仰ぐ質問で止まれるか。
  - 「スモークをお願いします」と言いかけたときに、ブロックされて自分で確認するか。
  - コミットの拒否と `winuse-gate: skip` が機能するか。
  - 「1 回だけブロック」の抜け道（一度ブロックされた後、同じ内容のまま完了報告する）が実際に起きるか。
  - セッション開始時に利用者の未コミット変更があっても、それだけでは止まらないか。
- 試運転で分かったこと（誤検知、逃げ道の使われ方、案 A の甘さ）を本ファイル末尾に追記する。

## 8. 成功の基準

- 利用者が「winuse で確認して」と指示しなくても、UI 変更のたびに AI が自分で確認してから完了を報告する。
- 試運転の間に、ゲートを外したくなるほどのうっとうしさが無い。

## 10. 実装で加わったこと（2026-10-26）

- 最終レビューの指摘で、セッションの cwd とは別のリポジトリ（worktree など）での編集もゲートの対象にした。Edit / Write / MultiEdit / NotebookEdit の後に非同期フック（`track-edit.ps1`、`"async": true`）で編集先のリポジトリを `<DataDir>\sessions\<session>.json` に記録し、Stop と証拠の記録はそれらすべてを見る。「1 回だけブロック」の記録もここに移した。シェルコマンドだけでの編集は拾わない。
- `git add ... && git commit` と `cd <dir> && git commit` / `Set-Location <dir>; git commit` もコミット前のゲートで判定する。
- 設定がセッション途中で壊れたら、Stop で 1 回だけ AI に知らせて利用者へ報告させる（§4.2 の「黙って無効にしない」）。

## 11. 試運転の準備で判明したこと

- MDium の `.gitignore` は `.claude` をまるごと無視していたため、`.claude/winuse-gate.json` をコミットできず、新しい worktree にも入らない。`.claude/*` と `!.claude/winuse-gate.json` に変えた（MDium ブランチ `chore/winuse-gate-config`）。プラグインの README にも同じ注意を書いた。
